The extractor flagged them all as NOT FOUND on first run against the real `Fwlib64.h`. → **Rule**: Never add a FOCAS function name to the target list, the spec doc, or the client without first grepping `Fwlib64.h` to confirm it exists. The function-name set differs between FS-16/18/21 and FS30i families, and our docs/training data leak the older names. R9 (FOCAS function name mismatch with reality) is exactly this risk — treat it as a structural hazard, not a one-time mistake.

**Mistake**: Decision-2 brief asked Claude to populate `tasks/spec-focas-calls.md` "verbatim from `C:\Fanuc\FwLib64-runtime\Fwlib64.h`" while the agent was in a Linux container with no Windows mount. → **Rule**: Header / SDK / DLL access lives on the Windows dev box. **Mistake**: First R1 mitigation in `migrations/env.py` checked only `op.schema` — but `CreateForeignKeyOp` stashes `source_schema` and `referent_schema` in `op.kw`, not as direct attributes. A migration creating an FK from `tooling.x` to `tracker.users` walked past the guard silently. → **Rule**: Any guard introspecting Alembic ops must walk both direct attributes ending in `schema` AND keys in `op.kw` ending in `schema`. Spot-check coverage with real op constructors — the text-scraping test harness we had didn't catch this because it didn't exercise FK ops.

**Mistake**: `_check_schema(schema, source)` returned early when `schema is None`, on the assumption "schemaless ops don't need checking." But Postgres routes unqualified DDL through `search_path`, defaulting to `public` — outside our allowlist. A bare `op.create_table('foo')` migration would happily land in `public.foo`. → **Rule**: `schema=None` means "fall through to the connection's search_path default" in Postgres. Treat it as forbidden, not safe. Pair with `SET search_path TO tooling, shared` on the migration connection so unqualified DDL has a safe deterministic landing zone (`tooling`).

**Mistake**: First R1 implementation was autogenerate-only — `process_revision_directives` and `include_object` only fire during `alembic revision --autogenerate`. A hand-written migration with a forbidden FK would never pass through them and would run unchecked at `alembic upgrade` time. → **Rule**: Schema isolation needs layered defense. (1) Runtime DDL inspection via SQLAlchemy `before_cursor_execute` is the primary line — fires on every cursor execute regardless of how the migration was authored. (2) Search-path lockdown on the connection. (3) Autogenerate-time op walker as early-warning. (4) Database-level GRANT as the ultimate belt. Code stops honest mistakes; DB GRANTs stop adversaries.

**Mistake**: First Phase 1 smoke against the real Viper failed with `cnc_allclibhndl3` returning -15 (`EW_NODLL`). The DLLs all existed on disk and `ctypes.WinDLL("Fwlib64.dll")` succeeded — but when the front-end DLL internally `LoadLibrary`'d its sibling `fwlibe64.dll` for the TCP transport, Windows couldn't find it. The first fix attempted `os.add_dll_directory`; the smoke still returned EW_NODLL. → **Rule**: `os.add_dll_directory` adds to the search path consulted by `LoadLibraryEx` with the user-dirs flag. Vendor DLLs that internally use plain `LoadLibrary` (the Fanuc front-end is one) ignore that list. The fix that actually works on Windows: (1) prepend the DLL directory to `PATH` (covers Standard Search Order), (2) preload every sibling DLL by absolute path before loading the front-end (puts them in the process's loaded-module table so subsequent short-name `LoadLibrary` calls find them by name in cache without filesystem lookup), (3) keep `add_dll_directory` as belt-and-suspenders. If a preload itself fails, its OSError names the real missing dependency (typically the MSVC runtime) — a much better diagnostic than the cryptic EW_NODLL coming back from `cnc_allclibhndl3`. The integration smoke caught both passes; it's the only mechanism that exercises the transitive DLL load path. Linux CI can't reproduce because `os.add_dll_directory` is Windows-only and the FOCAS DLLs don't exist on Linux.

**Mistake**: Second Phase 1 smoke against the real Viper got past EW_NODLL but crashed at `read_pots` with EW_NOOPT — and because `run_smoke()` called `source.read_snapshot()` as a single block that propagates exceptions, the entire report was lost. Every successful read before the failure (sysinfo, status, offset_layout, 1600 cnc_rdtofs calls' results) had to be reconstructed from scrollback. → **Rule**: Diagnostic / smoke scripts run against unfamiliar hardware MUST be resilient. Wrap every FOCAS section in its own try/except, accumulate failures into an `errors` list field, and always write the report file at the end regardless of which sections failed. Exit code reflects severity (0 = clean, 1 = some sections failed but report written, 2 = identity / R9 failure). The whole point of a smoke is to capture as much state as possible from one round-trip; a failure in section N must not lose the data from sections 1..N-1.

**Mistake**: Spent the entire O1 follow-up assuming the active T was somewhere in the **NC** layer (modal table, FANUC system macro `#4120`, or one of the documented FOCAS magazine functions). On a random-ATC machining center the active tool is **PMC ladder data**, not NC modal data — the magazine controller (separate microprocessor from the NC kernel) owns "what's in the spindle right now". Probes v1..v6 burned ~9 iterations chasing the NC layer: `cnc_modal` (datano sweeps `-20..20`, `100..130` × type `0,1,-1`) returned 0 every time; `cnc_rdtdiseltool` returned `EW_NOOPT`; no `#4xxx` / `#5xxx` system macro carried the panel head; `cnc_rdmagazine` returned `EW_NOOPT`; all seven secondary magazine functions (`cnc_rdcurmgr` / `cnc_rdcurpot` / `cnc_rdpotinfo` / `cnc_rdmagsts` / `cnc_rdspmaint` / `cnc_rdmgrptool`, plus `cnc_rdmagazine` itself) are not exposed by `fwlib30i64.dll` for this control. → **Rule**: For random-access tool changers (Mighty Viper class), assume HEAD / NEXT live in the PMC R-area as bytes from the start. The ATC ladder writes them; the NC kernel doesn't track them as modal. Reach for `pmc_rdpmcrng` immediately, not as a last resort. The "documented FOCAS function for active tool" set is for non-random ATCs and lathes.

**Mistake**: First PMC sweeps (probes v5 word-mode and v6 byte-mode) tried to find specific tool-ID values (`45`, `83`) by scanning every address in R/D/F/K/E. Result: zero hits — even though the values were definitely there at some moment, the machine was running and tools changed mid-sweep. Each sweep took 30-60 seconds; by the time we finished, head had advanced past the value we were looking for. → **Rule**: When the target value is on a moving machine, **never search for the value** — search for **what changes**. Snapshot/diff (`probe_modal_v7.py`) dumps the full PMC state, waits for a single observed transition, dumps again, and computes byte-level differences. The bytes that changed include the head register, pot table cells the indexer rotated, and a small amount of timer/counter noise. Filtering changed-byte list by "new value matches new panel head" pinpoints the storage regardless of byte/word/BCD encoding. The first dump after this approach: 4 changed bytes total, R321 went 25→85 — instantly identifiable as a tool-number register.

**Finding**: The Lance Viper's PMC ladder reads HEAD/NEXT through a scratch pointer at `R321` that flips between the stable storage at `R325` (NEXT) and `R327` (HEAD). A spot-read of R321 in Python returned different values on consecutive calls (31, then 85) because the ladder cycles through reading the two stable cells; we caught it mid-cycle. The actual storage is `R325` and `R327` — not `R321`. → **Rule**: When two consecutive reads of the same PMC byte return different values from a quiet machine, that byte is a **scratch register** the ladder uses internally — not the persistent state. Look at adjacent stable bytes (small even/odd offsets) for the source-of-truth values. Operator cross-check against the panel disambiguates within seconds.

**Finding** (Mighty Viper-specific OEM binding): On the Lance Viper LG-1000AP (Mighty Viper class, 24-pot random-ATC, FANUC 0i-MF Mate, FS30i processing DLL), the OEM PMC ladder stores the panel-displayed loaded-tool state at fixed R-area addresses: **R327 = HEAD** (tool currently in spindle), **R325 = NEXT** (tool to be called next), both as unsigned bytes carrying tool IDs 0..99. Address discovered by probe sequence v1→v9; confirmed against operator panel for both registers (`HEAD=85=R327`, `NEXT=31=R325`). → **Rule**: This binding is OEM-specific to the Mighty Viper PMC ladder, NOT a FANUC standard. Other random-ATC builders (Mazak, Doosan, Okuma, etc.) almost certainly use different R-addresses on their controls. Re-running `probe_modal_v7.py` (snapshot/diff workflow) is the per-machine identification path. Document the binding per machine in `tasks/spec-focas-calls.md` Verified-control-identity section, and never assume cross-machine.

**Mistake**: First soak attempt against the live Viper failed every cycle with `FocasError: FOCAS error -8 (cnc_statinfo)` immediately after a successful connect, while a sync diagnostic running the exact same FOCAS calls 5 minutes later worked perfectly. Initial hypothesis: rapid reconnect storm exhausted a FANUC daemon-side resource. Second hypothesis: `cnc_sysinfo` is required as the first call on a fresh handle to "prime" it before `cnc_statinfo` / `cnc_modal` will succeed (added as `FocasClient.connect()` end-step). Both wrong — the soak still failed even with the prime in place. **Real cause**: Windows FOCAS handles are **thread-affined**. The handle returned by `cnc_allclibhndl3` must be used by the same OS thread for every subsequent call (including `cnc_freelibhndl`). The async poller created the handle on the asyncio event loop thread (`run()` called `_connect()` synchronously) but dispatched reads via `asyncio.to_thread()` which uses the default `ThreadPoolExecutor` — a multi-worker pool. Cycle 1's read landed on worker A; cycle 2's read might land on worker B; even within a single cycle the handle creation thread differed from the read thread. Wrong-thread call → rc=-8 (which the FANUC docs document as `EW_HANDLE` for some calls). The diagnostic and smoke worked because they're pure-sync, single-threaded. → **Rule**: Any code path that uses a FOCAS handle across multiple async tasks MUST funnel every call (connect, every read, close) through a **dedicated single-worker `ThreadPoolExecutor`** owned by the lifetime of the handle. `asyncio.to_thread` is the wrong primitive. The `Poller.start()` creates `ThreadPoolExecutor(max_workers=1, thread_name_prefix=f"focas-{machine_id}")`; `stop()` shuts it down. Reconnects in the breaker recovery path stay on the same worker thread because the executor outlives any single connection. The CI mock harness can't catch this — it only surfaces when running against real DLLs on Windows. The sysinfo prime call is kept in `connect()` regardless (low-cost belt-and-suspenders, low-risk additive change).

**Mistake**: After the thread-affinity fix the async soak still appeared to "do nothing" for 30 minutes — operator was watching a Git Bash terminal that showed only the command echo, no progress logs, no warnings. Underlying cause: Python on Windows + Git Bash block-buffers stdout when the destination is a pipe-like terminal. Logger output (small per-line) doesn't reach the 8KB buffer threshold for ages. The actual report file (written every 5 min by `write_report()`) showed 2 successful cycles followed by a clean shutdown — proving the script was running fine but its progress was invisible. → **Rule**: Long-running CLI scripts that log progress MUST force line-buffering at startup: `sys.stdout.reconfigure(line_buffering=True)` plus `logging.basicConfig(..., force=True)`. Without this, Git Bash on Windows hides ALL log output until the script exits (or until ~8KB accumulates, whichever first). The smoke script worked unbuffered because it printed early + finished within a minute; the soak's 60-min runtime made the bug observable.

**Mistake** (surfaced by the safeguard-#4 backup/restore drill): A schema-scoped `pg_dump --schema=tooling --schema=shared -Fc` does **NOT** include the `pgcrypto` extension, even though pgcrypto lives *in* the `shared` schema. Restoring that dump into a fresh database fails on the very first `CREATE TABLE` with `ERROR: function shared.gen_random_uuid() does not exist` — every table's `id` PK defaults to `shared.gen_random_uuid()`, and the function is gone because the extension was never dumped. All 53 objects failed to restore. This would have bitten the first production DR restore or any pre-migration restore-into-scratch verification. → **Rule**: a schema-scoped restore target must have the extension pre-created **before** `pg_restore`: `CREATE SCHEMA shared; CREATE EXTENSION pgcrypto WITH SCHEMA shared;` (the dump then re-issues `CREATE SCHEMA shared`, producing one benign "already exists" error — any *other* error is real). Documented in `docs/runbooks/backup-restore.md`. General principle: extensions are database-level objects that `pg_dump -n/--schema` silently omits; any schema-scoped backup procedure must account for every extension the schemas depend on. A backup you have not actually restored into a fresh DB is a rumor, not a backup — the drill is the only thing that catches this.

**Finding** (Phase-4 auth slice, live contract check): **port 8000 is already occupied on the shared box** (Lance CNC Tracker's dev server — `netstat` shows a LISTENING PID). **Finding** (Mighty Viper pot-table discovery — OEM binding + BCD gotcha): FOCAS `cnc_rdmagazine` is `EW_NOOPT` on the Lance Viper (magazine option unlicensed), so the pot table is unavailable through the documented FOCAS surface. We reverse-engineered it from the PMC via `pmc_rdpmcrng` (read-only) using combined static-dump + tool-change-diff, then locked it against operator ground truth (pot1=T1, pot2=T90, pot3=T33). **Binding: pot table = PMC D-area, `D105`=pot 1 … `D128`=pot 24; `D104` = tool currently in the spindle. Values are BCD** (tool T90 stored as byte `0x90`=144, T33 as `0x33`=51). Cross-checked two ways: `D104` flipped `0x30→0x50` (T30→T50) on the tool change we watched, and the displaced T30 reappeared in its home pot 4. **Two traps this exposed:** (1) my candidate-finder filtered windows to values `0..99`, which *excludes* every BCD tool ≥ 80 (0x80=128) — a BCD table can never look like a raw table, so a raw-integer heuristic silently rejects it. (2) Searching for the raw decimal value 90 found *nothing* anywhere in the PMC — the tell that the encoding is BCD, not raw. → **Rule**: on FANUC PMC, assume tool/pot numbers may be **BCD** — if a known value (e.g. an operator-confirmed tool number) is absent from every area as a raw byte, re-search its BCD byte (`(n//10)<<4 | n%10`) before concluding it's not there. Anchor pot-table searches on a *distinctive* known value (T90, not T1) and allow a stride (word vs byte). This binding is **OEM-specific to the Mighty Viper ladder** (like the R327/R325 head/next binding) — the AG100/other builders need their own probe; never assume it ports. Document per-machine in `tasks/spec-focas-calls.md`.

**Empty-pot sentinel (operator-supplied, critical):** an empty pot on this Viper reads **its own ordinal** — pot 18 empty → BCD 18, pot 24 empty → BCD 24. Cause: when an operator mistakenly **resets the machine mid-tool-change**, the tools are physically ejected and the PMC pot table is **reinitialized to pot N = N** for all 24. So the initial map we decoded had pots 18–24 = 18…24 = **empty**, not "T18…T24". → **Rule (and a real hazard the app must respect)**: PMC value **== pot ordinal is ambiguous** — it's an empty/reinitialized pot in the common case, BUT collides with a genuinely-loaded tool whose number equals its pot (e.g. pot 1 legitimately holds T1, also reads 1). **The PMC alone cannot disambiguate.** Resolve it with the app's own identity records: a pot reading its ordinal with **no matching active assignment on this machine** → treat as empty; with a matching assignment → loaded. This is exactly the R10/R11 split (machine = observed state, app = identity/truth). Bonus safety hook: a *sweep* of pots reverting to their ordinals is the signature of the reset/reinit accident — the poller could **alarm** on it ("pot data reinitialized; tools may have been physically removed"). Open question: a pot emptied *normally* (unloaded without a reset) — does it read `0` or its ordinal? **ANSWERED (operator): neither reliably — the pot cell is STICKY. A normally-unloaded pot retains the *last tool number* that was there (or the ordinal after a reinit). So the PMC pot value NEVER reliably means "occupied" — it only carries the tool's nominal *identity*, never presence.** → **Rule (reframes pot occupancy entirely): the source of truth for "a real, usable tool is in this pot" is the OFFSET, not the pot cell.** A tool only becomes real when it's measured on the **tool presetter**, which writes its length offset (H register); decommissioning zeroes the offset. So occupancy = **offset non-zero** (measured tool present), **offset zero** = empty — regardless of the sticky pot value. This is also the *machining-correct* definition: a pot with a tool but no valid offset is unusable/dangerous (R6) anyway. Operational convention (operator confirmed, easy to adopt): **zero offsets (and pots) when a position is not in use** — that makes the map exact, no heuristics. The pot PMC table (D105-128) supplies IDENTITY (which T# nominally lives where); the mirrored offset table supplies PRESENCE. Correlate the two. The presetter-write is the *event* that flips a pot to "loaded/verified"; watch offset transitions (0→value = tool set; value→0 = removed) — the persist path already diffs+audits offset changes, so this is correlation, not new plumbing. Open: H-number == T-number convention? (would make pot→T→offset direct); and is there a "toolsetter active" PMC bit to attribute an offset change to the presetter vs a manual keypad edit (matters for audit trust, not for occupancy).

**CONFIRMED live (operator-driven experiment, 2026-07-08):** zeroed geometry offset **#21** (`3.4744 → 0`), ran the presetter to completion, and it wrote **`5.6883`** back to `h_geom` register #21 — read back verbatim via `read_offsets()`. Only that one register changed (clean diff). The write coincided with a **fresh G31 skip** (`#5061 -5.51→-4.01`, `#5063 3.93→4.35`), and the macro copies the skip into `#111-#113`. So the full chain is proven: *presetter G31 touch → skip latched (#5061-63) → macro computes length → writes the H-geom offset register → app reads it live*. **Design conclusions locked:** (1) offset non-zero = measured tool present, `0` = empty — occupancy is now a fact, not a heuristic; the persist path already diffs+audits offset changes so the app already detects presetter writes. (2) **Attribution:** an offset change **correlated with a fresh G31 skip** = presetter-verified; an offset change with **no** skip = manual keypad edit (the R11 trust signal). Reading the skip vars during polling needs `cnc_rdmacro` bound in the client (currently only in the standalone `scripts/probe_presetter.py`). Note `cnc_rdmacro` ODBM decode: `value = mcr_val / 10^dec_val`, `dec_val == -1` means the variable is vacant. Gotcha proven this session: re-presetting a tool whose offset was **already correct** writes the *same* value → **no diff** — to test/observe a presetter write, zero the offset first so the change is 0→measured and unmistakable.

**Finding** (Phase-C CI): the DSN guard's dev fingerprint is **local host AND port 5433** (not the DB name). That makes CI trivially safe *and* runnable without `LANCE_ALLOW_PROD`: map the GitHub Actions `postgres` service to **host port 5433** (`ports: ["5433:5432"]`) and point `DATABASE_URL` at `localhost:5433`. **Finding** (Phase 3 data-model gap surfaced during API build): Decision-4 locks the Viper probe at **T50 AND H50**, and R12 requires the API to reject assignments to either. But `shared.machine` shipped (migration 0001) with only `probe_t_number` — there was **no column for the probe H register**. The T50 rule was enforceable; the H50 rule was not, without hardcoding `50`. A single `probe_t_number` silently only half-enforces the lock.
